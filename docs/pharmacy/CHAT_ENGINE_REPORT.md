# Pharmacy chat engine (wave 2a): report

Branch `feat/pharmacy-niche`, local only. Everything lives in `apps/api/src/modules/chat/` (+ `apps/api/test/`). No schema or migration change was needed.

## 1. What is done

Principle kept: **code decides safety and money, the model only phrases.** For a pharmacy the engine runs *before* the model on every visitor turn and works with the model completely unavailable (every scenario below runs with zero model calls; a "hostile" stub model that would sell/recommend is never consulted).

## 2. Interfaces other agents must call / implement

1. **`ChatHumanService`** (exported by `ChatModule`): `recordHumanReply({ businessId, conversationId, author: { memberId, name, roleName }, text })` writes the banner once per person (`role: "system"`, `kind: "human_joined"`, content `"Nome · Função entrou na conversa"`, `uiData {type:"human_joined"}`) then the `role: "owner"` message with `authorMemberId/authorRole/authorName`; `recordHumanJoin(...)` banner only (a member taking over without replying). **2b's `POST /handoffs/:id/reply` should call it** (it still owns handoff status, access log, push) and so should any inbox/employee reply path (`InboxService.reply` today writes a bare owner message and requires `status: escalated`; I did not touch it).
2. **Order port**: `PHARMACY_ORDERS_PORT` (default `PrismaPharmacyOrders`, `useExisting` in `ChatModule`). Wave 3 may bind it to 2b's `OrdersService.createFromCart` (shape in `chat/pharmacy/types.ts` `CreateOrderInput`/`CreatedOrder`; it must accept `items[].viaEquivalentOf`, `requirePharmacist`, `addressDiffersFromSaved`, and return `status`, `statusToken`, `autoConfirmed`, `hasPrescription`, `staleSheet`, `pendingReasons`). If it writes its own alerts set `handlesNotifications = true`. Handoffs and notifier ports are the same pattern (`PHARMACY_HANDOFFS_PORT`, `PHARMACY_NOTIFIER_PORT`).
3. **Prescription upload (2b)** must store `PrescriptionUpload.conversationId`, `orderId = null`, `status = pending`. The engine finds uploads by conversation, moves the pending Rx line into the cart on the next visitor turn or on the `rx.check` action (2d: call it right after a successful upload), attaches the ids at order creation.
4. **2d widget**: render `messages` (not only `message`) when present; new action types `cart.view`, `cart.clear`, `rx.check`; consent purpose `order_contact`; the review/saved address is intentionally masked for known customers (`addressLabel`); `statusUrl` is `NEXT_PUBLIC_CHAT_URL + /pedido/<token>`. With a human in the conversation a new visitor message gets a short acknowledgement ("O farmacêutico vê sua mensagem...") and an answered handoff is set back to `open` by the engine (API.md 2.3).
5. **2b dashboards**: `briefRows` for the extra brief keys listed in API.md section 13 (`followUps`, out-of-stock `requestedProduct/stock/equivalents`, `suggestionNote`).
6. `AlertsService.createAlert` de-duplicates by `type` while an alert is active, so a `critical` urgent handoff alert can be hidden by an older active `warning` of the same type. Not mine to change; 2b may want a separate type for urgent ones.

## 4. Not done / known limits

- Product search is normalized-name/ingredient/keyword with typo tolerance; **no vector/embedding fallback** (PLAN/HANDOFF mention one). Postgres `contains insensitive` does not fold accents, so for accented names typed without accents the first DB pre-filter can miss; an in-memory scan of up to 3000 active products then runs (only when a token has >= 5 letters), so catalogs above that size could miss unusual spellings.
- Customer notifications by e-mail and visitor web push on pharmacist reply are 2b's; the engine only writes `BusinessAlert`s. Hours are not blocking (an order outside opening hours is accepted for the next opening, review says so).
- `pharmacy_checkout_abandoned` is emitted only on explicit cancel (no timer-based abandonment).
- Symptom -> suggestion mapping is a small fixed table (pharmacist-only list, never customer-visible); it is a convenience, not clinical logic, and should be reviewed by the responsible pharmacist.
- The pharmacy never asks for the WhatsApp in the symptom lane (the handoff is tied to the conversation; reply arrives in the chat). Phone is asked at checkout only.
- Concurrency: two simultaneous turns of the same conversation can overwrite each other's `pharmacyState` (same as other conversation state in this codebase).
- Legacy `TODO(wave2:chat-engine)` comments in `flow.service.ts`, `simulator.service.ts`, `listing-suggestions.ts`, `financing-rates.service.ts` still say "wave 2"; the behavior they describe (nothing listing/financing related for pharmacies) is final and the pharmacy lanes are in `chat/pharmacy/`.
- Assumptions to confirm with the owner/pharmacist: delivery areas empty = no restriction; unconfirmed OTC/Rx class is treated as "unclassified" (no online order); a red flag blocks cart add/confirm for 30 min; e-mail at checkout may be skipped.

## 5. Round 2 (owner feedback): what changed in the chat engine and widget

Everything below is deterministic (zero model calls), covered by `apps/api/test/pharmacy-round2.test.ts` (22 tests).

- **AI disclosure lives in the name.** Every Alex message label and the header read `Alex (IA)` (the separate "IA" pill is gone, the CRF / responsible pharmacist line stays). Welcome (persona + scripted start + widget fallback): `Oi! Eu sou o Alex, da <Farmácia>. Posso montar seu pedido ou chamar o farmacêutico.` (attendance: `... Posso tirar dúvidas sobre horários, entrega e retirada, ou chamar o farmacêutico.`). Footer line: `Não indico remédios nem dou orientação médica.` Human members keep `Nome · Função`.
- **One-tap, ask-once consent.** The consent card is the notice text plus the button that IS the consent (no checkbox): symptom (`Concordo e quero continuar` / `Só chamar o farmacêutico`), checkout contact (`Concordo e continuar`, only on the full form), prescription (`Concordo e tirar foto` / `Concordo e escolher arquivo`), WhatsApp contact (`pharmacy_contact`). Granted purposes (`pharmacy_triage`, `order_contact`, `prescription_upload`, `pharmacy_contact`) are kept in `pharmacyState.consents` and re-read from the lead's `ConsentRecord`s once the lead is recognized (phone-first), so a card is never shown twice for a purpose. Already captured phone/name/e-mail are never re-asked (the symptom lane skips the WhatsApp question when a phone is known). The widget never sends `consent: true` for a notice it did not show.
- **Consent loop bug (owner report).** Root cause: after a typed phone the engine asked for name/e-mail with a card that had a consent checkbox but no name field (and an empty optional e-mail was treated as "ask again"), so the form posted only `consent: true` and the same card came back, again and again; "não concordo" ended the checkout. Fixed: the follow-up card has the missing fields and carries the notice only on the full form; an empty optional e-mail means skip; declining explains the options (agree to continue, talk to the pharmacist, or visit the store) and keeps the question open, never switching to pickup. Regression test: `REGRESSION consent loop`.
- **Lane F answers the info chips.** `Horários e entrega`, `Horário de funcionamento`, `Taxa de entrega`, `Quero ver todas as informações` (and natural phrasings, "abrem/fecham/funcionam", ...) are answered from `PharmacySettings` in markdown blocks (hours per weekday + open/closed now, delivery fee/minimum/areas, pickup, payment, exchange policy for the full summary) followed by `Fazer um pedido` / `Falar com atendente`. They work in the middle of any state (the open question is repeated afterwards). Root cause of the old "posso ajudar com isso, o que você quer saber?": the widget's scripted bubble went to the flow node `outras`; pharmacy bubbles now go through the engine as text.
- **Unknown non-clinical questions -> attendant.** `Não tenho essa informação agora. Vou pedir para a equipe da farmácia confirmar e te respondo aqui mesmo.` plus a `PharmacistHandoff` with reason `general_question` (one per question, summary = the question text), notified through the notifier (alert `Nova pergunta de cliente aguardando resposta`, never the text). Triggers: (a) deterministic topics the settings never cover (holidays not in the opening hours, promotions/discounts, parking, invoices/receipts) and a configured topic with nothing configured; (b) the model path returning a pure "I don't have this information" (or being down) for a question that is not clinical (`ChatService` calls `PharmacyChatService.handleUnknownQuestion`). Clinical/symptom/dose questions still go to the pharmacist. Phone/name are asked only when unknown (`pharmacy_contact` consent remembered); the lead is then attached to the handoff. The chip `Falar com atendente` asks the question first, then creates the same handoff. Known limit: deterministic topics (a) are answered by the team even if the knowledge base happens to mention them (KB-first applies only to (b)).
- **Pharmacist suggestion -> purchase.** A `Message` (role owner) with `uiData { type: "pharmacist_suggestion", from, note?, items[] }` renders as a card (`Indicado por <nome> · <função>`, rows with image/name/price/stepper/`Adicionar`, `Adicionar tudo ao carrinho`, unavailable rows disabled `Sem estoque` / `Indisponível online`, Rx items start the prescription flow). History refreshes live price/stock/class (`hydrateMessages`). Engine: action `cart.add_many {productIds[] | items[{productId,qty}]}` (same class/stock/limit rules as `cart.add`, controlled/unclassified/unconfirmed never enter, Rx waits for the photo). With a suggestion newer than 14 days in the conversation, `quero comprar / quero esses / vou levar / pode ser / quero o primeiro / Fazer um pedido` buy THOSE items (`Vou separar o que o farmacêutico indicou:` + cart, blocked items explained); `ver outros produtos` / `o que mais tem` always show the catalog, and after the suggestion was bought `Fazer um pedido` is the catalog again. Only the newest suggestion and the newest cart card are interactive; opening a resume link scrolls to the newest message and the actions carry `?t=<resumeToken>`.
- **Quantity typed in the chat.** `quero 2`, `coloca 2`, `mude para 2`, `na verdade são 3`, `só 1`, `mais um/dois`, `tira um`, `remove / tira esse`, `quero 3 da dipirona` (sets a line already in the cart) adjust the focused / last-added line with the per-order limit and stock checked (clear messages, line kept) and answer with the cart card, which has `−` / `+` / `Remover` per line (the `+` stops at `maxQty`).
- **Address asked once.** The confirmed address (`knownAddress`) is reused by every later checkout of the conversation (`Usei o endereço que você já confirmou.` + chip `Informar outro endereço`), a saved default is confirmed once, pickup never asks for an address and keeps the confirmed one for later. Test: `delivery asks the CEP once ...`.
- **Symptom questionnaire age by patient.** `Para mim` / `Para outra pessoa adulta`: `18 a 29`, `30 a 59`, `60 anos ou mais`; `Para uma criança`: `Menos de 2 anos`, `2 a 5`, `6 a 11`, `12 a 17`; `Para um bebê`: `Menos de 3 meses`, `3 a 11 meses`, `1 ano ou mais`. A typed age that cannot belong to the patient (35 for a child, years for a baby, 5 years for an adult) is asked again. The brief carries `forWhom.patient`, `pediatric` and an `attention` note (baby or child under 12 stay flagged); no stock-based suggestion for under 2.
- Widget: older symptom chip rows disappear once a newer question exists (only the newest is live); the manual "Atualizar" button of the poll cap is gone for pharmacies (polling has no cap while the tab is visible and keeps going while any handoff is open: `pharmacy.handoffOpen`).
